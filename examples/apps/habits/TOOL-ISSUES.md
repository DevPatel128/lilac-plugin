# Tool issues found (not bent around in the app)

Tools: `operations/plugin/scripts/controls-test.mjs`, `persona-test.mjs`, `qa-browser.mjs`. Dated 2026-11-22. Each item: what the tool printed, why it is the tool.

1. controls-test, single-document hash-route app. Printed: `Help ... UNREACHABLE | never visible in any reachable screen (display none, zero size or off-screen) and not a skip link` for the Help, Settings, Support and dialog controls (77 in total, lines 55 to 104 of `.lilac/controls-run2.txt`). Why: all screens live in one HTML file and are hidden until the hash route shows them. The nav rows themselves print `OK navigated to /index.html#/help; DOM changed; focus moved to h2#h-help`, but the controls of the opened screen are never collected as a screen, and the later rows are all labelled `(after: Keyboard shortcuts)`, i.e. measured while the shortcuts modal is open (a modal makes the page behind inert). Not wired through: 0 dead, 0 broken.
2. controls-test leaks typed state. Printed: `Edit Drink water (after: Take the tour) | button | UNREACHABLE | covered by nothing`. Screenshot `.lilac/controls/Edit_Drink_water-1.png` shows search box text "Sample text" and "No habits match your search or filter": the tool typed into Search and never cleared it, so the list is filtered empty. By design the app filters as you type.
3. persona-test treats a click on a hash link, and `Page.navigate` to a URL that differs only by hash, as a page load. Printed: `why: page did not finish loading within 8s` for task `nav` (28 sessions), `/#/settings did not finish loading within 8s` (run 1). A same-document navigation fires no load event. Workaround in `.lilac/personas.json` only: each custom task starts at `/index.html?t=N#/route`. The built-in `nav` task cannot be worked around: 0% (0/28).
4. persona-test shares storage between concurrent sessions in one Chrome profile (6 at a time). Likely cause, not proven. Evidence: `"Add your first habit" exists but is hidden` (a habit from another session exists) and `nothing to click that says "Water plants, today"` for `custom:mark it done` (0/18). Own tasks depend on a fresh store; sessions are not isolated.
5. persona-test contact task is built for multi-page sites. Printed: `"Write an email" exists but is hidden` (it lives on `#/support`, a different screen), and it picked a habit card as a contact candidate: `"Water plants Streak 0 days ... Edi" is not keyboard-focusable (<li> with a mouse handler, not a link or button)`. The `<li>` holds real buttons (Edit, Delete, day buttons) and is not itself a control.
6. persona-test screen-reader proxy: `"Add your first habit" is not exposed to assistive technology as a control (<button> without a role)` and `"Write an email" ... (<a> without a role)`. A native button and link have implicit roles. The tool only looks for an explicit role attribute.
7. persona-test skimmer and no-JS personas run custom tasks although `personas.json` lists other personas for them (skimmer 6/18, no-js 4/12). Skimmer reads links only and this app is button-based; a no-JS visitor sees the `<noscript>` message because the app needs JavaScript. Both are expected, not defects.
8. qa-browser `[text-overlap]` warning is the fixed first-visit toast over footer text at scroll top (see RESULTS.md, accepted).

Not a tool issue (own task bug, fixed): the first personas file expected "Add your first habit" in every session and ended tasks on Settings; it now starts each task on its own route.

9. controls-test (run 3, after the single-page-app fix) `Next (after: Take the tour) | button | UNREACHABLE | covered by nothing; screenshot .lilac/controls/Next-1.png`. The screenshot shows no dialog open: the tool clicks Next in a state where the tour is already closed. `tests/state-checks.mjs` proves Next, Back and Skip work at 360, 768 and 1280 px. Items 1 and 2 above applied to run 2 and are fixed in run 3 (81 controls, 5 unreachable). `about: Reload to update`, `Clear search and filter`, `OK` and `Back` are state-conditional (see RESULTS.md, State-conditional controls).
